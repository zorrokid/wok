# 011: Scrolling Tilemap with Tiled Editor & Physics Integration

## Overview
Migrate from hardcoded level data to the Tiled map editor using TMX format, integrate Avian2D physics for collision detection, and implement camera bounds for horizontal scrolling. This enables visual level design in Tiled, physics-based player movement, and supports large scrolling levels. This is a comprehensive refactor that modernizes the level system and replaces custom collision with industry-standard physics.

## Current State
- Level data hardcoded as 20x15 Rust const array (`LEVEL_DATA`)
- Manual `TilemapBundle` setup in `level/mod.rs`
- Custom tile-based collision detection (`world_to_tile_coords`, `get_tile_type_at`, `is_grounded`)
- Custom `Velocity` component and gravity/jump physics
- Camera follows player smoothly but has no bounds (spec 005)
- Level is small (320x240 pixels), fits on screen

## Requirements

### Tiled Editor Integration
- Use Tiled map editor for level design instead of hardcoded arrays
- TMX format for maps
- Load maps using `bevy_ecs_tiled` plugin
- Support for 16x16 orthogonal tile maps
- Use existing `tileset.png` as the tileset

### Physics Integration
- Replace custom collision with Avian2D physics engine
- Player uses `RigidBody::Dynamic` with physics collider
- Tile colliders auto-generated by `bevy_ecs_tiled` as `RigidBody::Static`
- Ground detection via Avian2D `ShapeCaster` instead of custom tile checks
- Gravity, jumping, and movement handled by physics system

### Scrolling & Camera Bounds
- Level width significantly larger than viewport (100+ tiles wide)
- Camera follows player horizontally within level bounds
- Camera stops at level edges (doesn't show empty space beyond tilemap)
- Camera smoothly tracks player using existing lerp system
- Vertical camera behavior remains unchanged (follows player on Y axis)

## Implementation Plan

### Approach Overview
This is a comprehensive refactor in 3 major parts:

1. **Tiled Integration**: Replace `LEVEL_DATA` const array and manual `TilemapBundle` setup with `bevy_ecs_tiled` plugin loading TMX files
2. **Physics Migration**: Replace custom collision detection (`world_to_tile_coords`, `check_feet_tiles`, `is_grounded`, `ground_snap_y`) with Avian2D physics (`RigidBody`, `Collider`, `ShapeCaster`)
3. **Camera Bounds**: Add horizontal clamping to `camera_follow()` based on level dimensions

### Reference Implementation
Following the `bevy_ecs_tiled` `demo_platformer` example pattern:
- Player: `RigidBody::Dynamic`, `Collider`, `ShapeCaster` for ground detection, `LockedAxes::ROTATION_LOCKED`
- Tiles: Auto-generated `RigidBody::Static` colliders via `TiledPhysicsPlugin`
- Movement: Avian2D `LinearVelocity`, `MovementAcceleration`, `JumpImpulse`, `Gravity`

### Technical Details

#### Physics Constants Tuning
Match the original feel by tuning these values:
- `Gravity(Vec2::NEG_Y * 980.0)` — Global gravity resource
- `PLAYER_ACCELERATION: f32 = 800.0` — Acceleration toward target speed
- `PLAYER_DECELERATION: f32 = 1200.0` — Deceleration to zero (faster than accel for snappy stops)
- `JUMP_VELOCITY: f32 = 400.0` — Jump impulse (tuned up from original 300 to clear highest platform)
- `PLAYER_MAX_SPEED: f32 = 100.0` — Horizontal speed cap

#### Camera Bounds Formula
The camera bounds ensure that the viewport edges don't extend beyond the level:

```
Viewport shows world positions: [camera_x - viewport_width/2, camera_x + viewport_width/2]

For viewport to stay within level [level_left, level_right]:
  camera_x - viewport_width/2 >= level_left
  camera_x + viewport_width/2 <= level_right

Therefore:
  camera_min_x = level_left + viewport_width/2
  camera_max_x = level_right - viewport_width/2
```

#### Viewport Size
For now, use hardcoded viewport dimensions (800x600). Future enhancement: query window size dynamically.

#### Edge Cases
- **Small level**: If `level_width < viewport_width`, set `camera_min_x = camera_max_x = level_center_x` to center the level
- **Player near edge**: Player can walk to level edges; camera stops but player keeps moving
- **Lerp at bounds**: Lerp target might be beyond bounds, but clamp ensures camera doesn't exceed limits
- **Tile alignment**: `TilemapAnchor::Center` centers the map on the world origin; Avian2D colliders are generated at the correct world positions relative to the tile positions

#### Tiled Map Configuration
- **Orientation**: Orthogonal
- **Tile size**: 16x16 pixels
- **Tileset**: External reference to `tileset.png`
- **Format**: TMX (XML)
- **Layers**: Single tile layer for solid platforms
- **Future**: Can add object layers for spawn points, enemies, collectibles using Tiled custom properties

#### Physics Backend Choice
Using Avian2D over Rapier because:
- Pure Rust (no C wrapper)
- Designed specifically for Bevy
- Well-maintained, active development
- `bevy_ecs_tiled` 0.11 supports Avian2D 0.5 with Bevy 0.18

#### Migration Risk & Mitigation
**Risk**: Physics feel may differ significantly from custom implementation
**Mitigation**:
1. Tune physics constants to match original values (gravity 980, acceleration 800, jump 300)
2. Add damping system for horizontal movement control
3. Test thoroughly and adjust constants as needed
4. Can add velocity clamping if Avian2D allows exceeding max speed

**Risk**: Build times increase with Avian2D dependency
**Mitigation**: Expected, but acceptable for physics quality and maintainability

**Risk**: Player may clip through tiles or feel floaty
**Mitigation**:
- Use `ShapeCaster` with appropriate max distance (10.0 pixels works reliably; 1.0 is too small)
- Tune collider sizes (slightly smaller than sprite to prevent edge catches)
- Adjust `MovementDampingFactor` if movement feels slippery

#### Why This Major Refactor?
1. **Scalability**: Visual level editor (Tiled) vastly easier than editing Rust arrays
2. **Industry standard**: Tiled is ubiquitous in 2D games, better workflow
3. **Physics quality**: Avian2D handles edge cases (slopes, moving platforms, one-way platforms) that would be complex to implement manually
4. **Future features**: Tiled custom properties enable data-driven entity spawning (enemies, collectibles, spawn points)
5. **Maintainability**: Less custom code to maintain, leverage community-supported libraries

#### Why Tiled/TMX vs Other Formats?
- **TMX (XML)**: Human-readable, easy to inspect/debug, git-friendly
- **LDTK**: Another excellent editor, but Tiled has broader adoption and better Bevy integration via `bevy_ecs_tiled`
- **Choice**: TMX for readability while developing

### Notes


#### Why Combine Tiled Adoption + Scrolling?
Both changes touch the level system, so combining them:
- Avoids double refactor (changing level loading twice)
- Natural progression: Tiled → larger levels → scrolling
- Single testing/verification cycle
- More cohesive spec documentation

Separate specs would have required:
- Spec A: Tiled + physics with same 20x15 level
- Spec B: Expand level + camera bounds

Combined approach is more efficient.

#### Alternative Approaches Considered

**1. Keep Custom Collision, Add Tiled Later**
Implement scrolling first with `LEVEL_DATA` expansion to 100 tiles.
- **Pros**: Smaller change, less risk
- **Cons**: Still have to edit 100-tile Rust array by hand, then redo it later for Tiled

**2. Tiled Without Physics Migration**
Use `bevy_ecs_tiled` but keep custom collision code.
- **Pros**: Incremental migration
- **Cons**: Need to query tilemap differently, collision code becomes more complex, misses benefits of physics

**3. Physics First, Tiled Later**
Migrate to Avian2D with current `LEVEL_DATA`, then add Tiled.
- **Pros**: Isolate physics changes
- **Cons**: Still editing hardcoded arrays, then refactoring again for Tiled

**Decision**: Combined approach is most efficient given that both changes require level system refactor.
